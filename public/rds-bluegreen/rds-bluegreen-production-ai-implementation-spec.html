RDS Blue/Green Readiness Gate 운영계 AI 구현 지시서

이 파일 하나만 보고 운영계 소스에 구현할 수 있도록 작성한 상세 명세다. 목적은 AWS JDBC Wrapper 내부 서비스 객체에 의존하지 않고, AWS SDK, 일반 JDBC, DNS, 인스턴스 discovery를 사용해 스위치오버 직전 모든 앱 인스턴스의 준비 상태를 판정하는 것이다.

wrapper service object 의존 없음 AWS SDK 기반 regional fanout pre-switchover gate

1. AI 구현 지시 요약

운영계 AI 에이전트는 아래 범위를 그대로 구현한다. 기존 AWS JDBC Wrapper의 `bg` plugin은 런타임 보호장치로 유지하고, 이 readiness gate는 switchover 버튼을 누르기 전 운영 절차에서 호출한다.

Build

앱 내부 collector 구현

AWS SDK RDS, 일반 MySQL JDBC, DNS resolve를 조합해 인스턴스 단위 readiness snapshot을 만든다.

Fanout

권역 단위 API 구현

EC2 tag 또는 운영계 service registry로 대상 인스턴스를 찾고 각 인스턴스의 readiness API를 호출한다.

Gate

스위치오버 전 차단 조건 구현

하나라도 실패하면 `allReady=false`로 switchover를 중단하고 사유를 로그/응답에 남긴다.

중요 결론

`DescribeBlueGreenDeployments=AVAILABLE`만으로는 완전히 신뢰할 수 없다. 실제 검증에서 deployment가 `AVAILABLE`이어도 target DB instance가 `modifying`인 동안 switchover가 실패했다. 따라서 `DescribeDBInstances(source/target).DBInstanceStatus == available`은 선택이 아니라 필수 조건이다.

Wrapper 수집 완전 커버 보강 지시

이 섹션은 운영계 AI 구현자가 반드시 읽어야 하는 추가 지시다. 기존 readiness gate는 pre-switchover 판단에 충분히 강하지만, AWS JDBC Wrapper 내부 준비 수집을 더 가깝게 커버하려면 아래 항목을 빠뜨리면 안 된다.

최종 목표 문장

운영계 구현은 "AWS에서 switchover 가능해 보인다"가 아니라, "wrapper가 SOURCE/TARGET monitor로 준비 단계에서 수집하는 상태, topology, DNS/IP, corresponding node 정보를 애플리케이션 외부 gate에서도 독립적으로 재확인했다"는 수준까지 도달해야 한다.

wrapper 내부 수집/준비 항목 wrapper 근거 운영계 API 구현 요구 현재 test-for 기준
SOURCE monitor와 TARGET monitor를 각각 실행 BlueGreenStatusProvider.initMonitoring()에서 SOURCE/TARGET BlueGreenStatusMonitor를 별도로 시작 source endpoint뿐 아니라 target endpoint도 직접 JDBC probe한다. 둘 다 metadata query와 DNS resolve가 가능해야 한다. 보강 필요
Blue/Green status table 조회 BlueGreenStatusMonitor.collectStatus()가 dialect의 getBlueGreenStatusQuery()를 실행 MySQL은 mysql.rds_topology, PostgreSQL은 rds_tools.show_topology(...) 또는 pg_catalog.get_blue_green_fast_switchover_metadata(...)를 dialect별로 분기한다. MySQL만 구현됨
HostListProvider topology 수집 BlueGreenStatusMonitor.collectTopology()가 hostListProvider.forceRefresh() 호출 source/target row만 세지 말고 writer/reader topology를 role별로 분리해 expected writer count, reader count, endpoint set을 검증한다. 부분 구현
시작 IP와 현재 IP 수집 collectHostIpAddresses(), updateIpAddressFlags() 각 endpoint의 DNS address set을 저장하고 source/target pair 간 IP가 겹치지 않는지 확인한다. 연속 호출 동안 IP set이 비정상적으로 흔들리면 실패 처리한다. 대부분 구현됨
correspondingNodes 생성 BlueGreenStatusProvider.updateCorrespondingNodes() writer pair뿐 아니라 reader pair도 mapping한다. reader 수가 다르면 wrapper처럼 round-robin 또는 writer fallback 규칙을 명시한다. 단일 pair 중심
PREPARATION/IN_PROGRESS/POST 라우팅 생성 getStatusOfPreparation(), getStatusOfInProgress(), createPostRouting() readiness API가 라우팅을 직접 구현하지 않는다. 대신 "이 영역은 wrapper 런타임 책임"으로 문서화하고, 운영계에는 wrapper bg plugin 활성화 검증만 둔다. 의도적으로 제외
POST 이후 green DNS 제거, blue DNS update, green topology change 감지 updateDnsFlags(), getStatusOfCompleted() pre-switchover gate에는 넣지 않는다. 별도 post-switchover verification API 또는 runbook으로 분리한다. 사후 검증 영역

AI가 반드시 추가 구현해야 하는 v2 항목

운영계 소스에 반영할 때는 현재 v1 조건에 아래 v2 조건을 추가한다. 이 항목들이 들어가야 "wrapper 준비 수집을 거의 커버했다"고 말할 수 있다.

V2-1

Target direct JDBC probe

AWS SDK로 target DB endpoint를 확인한 뒤, target endpoint로 직접 일반 JDBC connection을 연다. 이 연결은 쓰기 검증을 하지 않는다. metadata 접근성, topology/status query 가능 여부, DNS/IP 상태만 확인한다. 

targetProbeOk =
  targetDbInstance.status == "available"
  AND connect(targetEndpoint) succeeds
  AND blueGreenMetadataReadable(targetConnection)
  AND targetTopologyRows include TARGET role
V2-2

Reader topology mapping

source writer와 target writer만 맞추지 말고 reader endpoint 목록도 분리한다. 운영계에 reader가 없으면 writer-only topology로 명시하고, reader가 있으면 source reader마다 target reader 또는 target writer fallback을 mapping한다. 

writerPairs = pair(sourceWriters, targetWriters)
readerPairs = pairReadersOrFallbackToTargetWriter(
  sourceReaders,
  targetReaders,
  targetWriter
)
V2-3

Dialect abstraction

MySQL만 하드코딩하지 않는다. 운영 DB engine을 설정 또는 JDBC metadata로 판별하고, engine별 blue/green metadata query와 writer check를 별도 strategy로 분리한다. 

interface BlueGreenMetadataDialect {
  boolean isSupported(Connection c);
  String statusQuery();
  String writerCheckQuery();
  TopologySnapshot parse(ResultSet rs);
}

v2 candidateReady 식

candidateReadyV2 =
  awsReady
  AND sourceProbe.ready
  AND targetProbe.ready
  AND sourceProbe.currentWriter
  AND metadataDialectSupported
  AND sourceTopologyReadable
  AND targetTopologyReadable
  AND sourceVisible
  AND targetVisible
  AND writerPairingOk
  AND readerPairingOk
  AND allPairIpsDistinct
  AND dnsStableAcrossAttempts
  AND wrapperBgPluginConfigured

AI에게 그대로 줄 구현 프롬프트

아래 블록은 운영계 코드 수정 AI에게 그대로 전달할 수 있는 작업 지시다. 

너는 운영계 Spring/Java 애플리케이션에 RDS Blue/Green pre-switchover readiness gate를 구현한다.

절대 조건:
1. AWS Advanced JDBC Wrapper 내부 서비스 객체, BlueGreenStatusProvider, BlueGreenStatusMonitor 인스턴스에 의존하지 않는다.
2. AWS SDK, 일반 JDBC, DNS resolver, 운영계 service discovery만 사용한다.
3. 기존 AWS JDBC Wrapper bg plugin은 datasource runtime 보호용으로 유지한다. readiness API가 wrapper를 대체하지 않는다.
4. readiness API는 public internet에 노출하지 않는다.

구현할 API:
- POST /api/rds-bluegreen/readiness
- POST /api/rds-bluegreen/regional-readiness

반드시 구현할 collector:
- RDS DescribeBlueGreenDeployments
- RDS DescribeDBInstances(source/target)
- source endpoint direct JDBC probe
- target endpoint direct JDBC probe
- MySQL metadata dialect
- PostgreSQL metadata dialect
- DNS/IP resolver
- writer/reader topology mapper
- corresponding node mapper
- regional fanout target discovery

ready=true 조건:
- AWS deployment, tasks, switchover members ready
- source/target DB instance available
- source JDBC connect OK
- target JDBC connect OK
- source metadata readable
- target metadata readable
- source current connection writer
- source and target topology visible
- writer pairing OK
- reader pairing OK or explicit writer-only topology
- source/target pair IP distinct
- DNS stable across attempts
- required consecutive successes reached
- all regional instances ready

응답:
- boolean 하나만 반환하지 말고 blockingReasons[], warnings[], sourceProbe, targetProbe, topologyMapping, dns, awsDeployment, runtimeGuard를 포함한다.

테스트:
- deployment PROVISIONING
- deployment AVAILABLE but target DB modifying
- target endpoint JDBC timeout
- source metadata readable but target metadata unreadable
- reader count mismatch
- DNS resolve failure
- source/target same IP
- one instance not ready in regional fanout
- all instances ready then real switchover succeeds

2. 운영계 대상 아키텍처

이 구조는 "권역 하나, 내부 여러 브랜드, 브랜드별 다중 인스턴스"를 기본 전제로 한다. 운영자는 global 또는 regional API 하나를 호출하고, API가 내부 앱 인스턴스 전체로 fanout한다. 

flowchart LR
  Ops[Operator or pipeline] --> Regional[POST /api/rds-bluegreen/regional-readiness]
  Regional --> Discovery[EC2 tag or service registry discovery]
  Discovery --> A1[BRAND-A instance 1]
  Discovery --> A2[BRAND-A instance 2]
  Discovery --> B1[BRAND-B instance 1]
  Discovery --> B2[BRAND-B instance 2]
  Discovery --> C1[BRAND-C instance 1]
  Discovery --> C2[BRAND-C instance 2]
  A1 --> RDS[AWS RDS control plane]
  A1 --> DB[(Source DB)]
  A1 --> DNS[DNS resolver]
  A2 --> RDS
  B1 --> RDS
  B2 --> RDS
  C1 --> RDS
  C2 --> RDS
  Regional --> Decision{allReady?}
  Decision -- yes --> Switch[Call switchover-blue-green-deployment]
  Decision -- no --> Stop[Stop and show failed instances]

Mermaid가 로드되지 않는 환경에서는 위 원본이 그대로 보인다.

4. 구현 클래스와 책임

아래는 `test-for`에서 검증된 구조다. 운영계 프레임워크가 다르더라도 역할 분리는 유지한다.

파일/컴포넌트 운영계에서 구현할 책임 핵심 규칙
RdsBlueGreenReadinessController 인스턴스 단위 readiness endpoint. `attempts`, `delayMs` query parameter를 받는다. POST만 허용. 내부망 인증/인가 적용.
RdsBlueGreenReadinessService collector 결과를 최종 `candidateReady`, `ready`, `reason`으로 합성한다. 기본 3회 연속 `candidateReady=true`일 때만 `ready=true`.
RdsBlueGreenInternalReadinessCollector RDS control plane, DB metadata, DNS를 수집한다. wrapper 내부 객체를 호출하지 않는다. AWS SDK와 일반 JDBC만 사용.
RdsBlueGreenRegionalReadinessController 권역 단위 fanout endpoint. 운영자는 가능하면 이 API만 호출한다.
RdsBlueGreenRegionalReadinessService EC2/service registry discovery, private IP fanout, 브랜드별 summary 생성. 대상 0개면 `allReady=false`.
RdsBlueGreen*Snapshot records 수집 결과를 JSON 응답/로그로 보존한다. 실패 원인은 boolean만 두지 말고 `reason`, `errorClass`, `errorMessage`까지 둔다.

5. 판정식

구현자는 아래 식을 그대로 구현한다. 이 조건은 인스턴스 하나의 `candidateReady` 판정이다. 

candidateReady =
  awsReady
  AND dbConnectionOk
  AND currentWriter
  AND topologyReadable
  AND sourceVisible
  AND targetVisible
  AND dnsResolvable
  AND sourceTargetPairingOk
  AND sourceTargetIpsDistinct

ready =
  candidateReady가 requiredConsecutive 횟수만큼 연속 성공
조건 구현 방법 실패 reason 예시
awsReady deployment, switchover members, tasks, source/target DB instance가 모두 준비됐는지 확인 source or target DB instance is not available
dbConnectionOk 일반 MySQL JDBC로 source endpoint 접속 database metadata check failed
currentWriter select @@read_only가 false인지 확인 current regular JDBC connection is not writer
topologyReadable mysql.rds_topology row 수가 최소 2 이상인지 확인 mysql.rds_topology rows 1 < 2
sourceVisible / targetVisible topology role에 SOURCE/TARGET row가 있는지 확인 target topology row is not visible yet
dnsResolvable topology endpoint별 InetAddress.getAllByName 수행 one or more topology endpoints are not DNS-resolvable
sourceTargetPairingOk source endpoint와 target endpoint가 같은 논리 노드의 pair인지 확인 source and target topology rows are not logically paired
sourceTargetIpsDistinct source/target DNS 결과 IP set이 서로 disjoint인지 확인 source and target topology endpoints do not resolve to distinct IP addresses

6. AWS SDK 수집 규칙

AWS JDBC Wrapper 내부 모니터링 객체를 쓰지 않고 운영계 앱이 직접 수집한다.

DescribeBlueGreenDeployments

대상 deployment 찾기

  • 우선순위 1: `RDS_BG_DEPLOYMENT_ID`로 정확히 조회한다.
  • 우선순위 2: `RDS_BG_SOURCE_ARN`, `RDS_BG_TARGET_ARN` filter로 찾는다.
  • pagination marker를 끝까지 따라간다.
  • status는 `AVAILABLE` 또는 switchover 이후 관측 목적의 `SWITCHOVER_COMPLETED`를 ready로 본다.
DescribeDBInstances

source/target 실제 DB 상태 확인

  • deployment의 `source`, `target` ARN에서 DB instance identifier를 추출한다.
  • 각 identifier에 대해 `DescribeDBInstances`를 호출한다.
  • source와 target의 `DBInstanceStatus`가 모두 `available`이어야 한다.
  • 이 조건이 없으면 deployment `AVAILABLE`인데 switchover 실패하는 구간을 막지 못한다.
awsDeploymentReady =
  deployment.status in ["AVAILABLE", "SWITCHOVER_COMPLETED"]

switchoverMembersReady =
  all member.status in ["AVAILABLE", "SWITCHOVER_COMPLETED"]

tasksReady =
  all task.status == "COMPLETED"

dbInstancesReady =
  sourceDbInstance.status == "available"
  AND targetDbInstance.status == "available"

7. DB와 DNS 수집 규칙

11. 구현 순서

  1. 의존성 추가AWS SDK BOM, RDS client, EC2 client를 추가한다. 기존 DB driver와 JSON mapper는 서비스 표준을 사용한다.
  2. 설정 모델 추가RDS API, regional fanout, readiness log, DB 접속 정보를 properties로 만든다.
  3. 인스턴스 readiness API 구현controller, service, collector, result records를 추가한다.
  4. RDS control plane 수집 구현`DescribeBlueGreenDeployments`와 `DescribeDBInstances`를 모두 구현한다.
  5. DB metadata 수집 구현일반 JDBC로 writer 여부와 `mysql.rds_topology`를 확인한다.
  6. DNS와 pair 검증 구현source/target endpoint resolve, logical pairing, IP distinctness를 구현한다.
  7. regional fanout 구현EC2 tag 또는 회사 service registry로 대상 인스턴스를 찾고 private endpoint로 fanout한다.
  8. 로그/응답 증적 구현인스턴스 상세 로그와 권역 summary 로그를 남긴다.
  9. 보안 적용내부망 제한, 운영자/파이프라인 인증, rate limit, audit log를 적용한다.
  10. 실제 switchover rehearsalstaging에서 `allReady=true` 직후 switchover를 수행하고 `SWITCHOVER_COMPLETED`까지 확인한다.

14. 운영 런북

  1. Blue/Green deployment 생성AWS CLI, console, IaC 중 운영 표준 방식으로 생성한다.
  2. deployment ID 전파모든 앱 인스턴스에 같은 `RDS_BG_DEPLOYMENT_ID`가 들어가야 한다.
  3. AWS 상태 1차 대기deployment `AVAILABLE`까지 기다리되, 이것만으로 switchover하지 않는다.
  4. regional readiness 호출`POST /api/rds-bluegreen/regional-readiness?attempts=5&delayMs=1000` 호출.
  5. 증적 저장응답 JSON과 `RDS_BLUE_GREEN_READINESS_SUMMARY` 로그를 저장한다.
  6. allReady 확인`allReady=true`, `notReadyInstances=0`, 브랜드별 expected count 일치 확인.
  7. switchover 실행가능하면 readiness 성공 직후 자동으로 `switchover-blue-green-deployment` 호출한다.
  8. 완료 확인AWS 상태가 `SWITCHOVER_COMPLETED`인지 확인한다.
  9. 사후 검증앱 write/read smoke test, DB writer 확인, wrapper bg plugin 런타임 로그를 확인한다.
  10. cleanup 계획old blue, 스냅샷, 수동 생성 리소스, Terraform drift를 별도 절차로 정리한다.

15. 절대 하지 말아야 할 것

이 API만으로 무장애를 보장한다고 표현하지 말 것

이 장치는 switchover 전 gate다. switchover 중 JDBC connection/query 보호는 AWS JDBC Wrapper `bg` plugin 또는 동등한 런타임 전략이 맡는다.

외부 공개 API로 노출하지 말 것

DB endpoint, deployment identifier, instance id, 내부 상태가 응답에 들어간다. 내부망과 운영 권한으로 제한해야 한다.

대상 인스턴스 수를 검증 없이 넘어가지 말 것

`allReady=true`여도 discovery 대상 수가 기대값보다 적으면 운영자가 모르는 누락이다. 브랜드별 expected count 검증을 runbook에 넣는다.

deployment ID 전파를 수동 기억에 맡기지 말 것

모든 앱 인스턴스가 같은 BGD ID를 보도록 pipeline 변수, SSM parameter, config refresh 절차를 명확히 둔다.
