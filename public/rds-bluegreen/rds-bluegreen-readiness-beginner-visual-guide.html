DB를 새 DB로 바꾸기 전, 왜 확인 버튼을 눌러야 하나

이 문서는 DB 교체 작업을 처음 보는 사람도 이해할 수 있게 쓴 안내서다. 핵심은 하나다. 새 DB로 바꾸기 전에 우리 서버들이 정말 준비됐는지 먼저 물어봐야 한다.

쉬운 말 중심 처음 읽는 사람 기준 운영 전 판단 연결 도우미 비교 포함

한 문장으로

DB 교체는 이사와 비슷하다. 새집이 준비됐는지, 주소가 맞는지, 가족 모두가 새 주소를 알고 있는지 확인한 뒤 이사해야 한다.

서비스고객이 실제로 쓰는 앱
현재 DB지금 데이터를 읽고 쓰는 곳
새 DB곧 바꿔 탈 곳
확인 버튼바꾸기 전 마지막 질문

1. 이 문서는 어떤 상황을 설명하나

회사 서비스는 DB에 고객 정보, 주문 정보, 설정값 같은 중요한 데이터를 저장한다. DB를 새 버전으로 바꾸거나 더 안전한 구조로 바꾸려면, 기존 DB 옆에 새 DB를 만들어 두고 어느 순간 새 DB로 갈아탄다.

처음 읽는 사람은 이것만 기억하면 된다

지금 서비스는 현재 DB를 보고 있다. AWS가 새 DB를 옆에 만들어 준다. 운영자는 새 DB가 준비됐다고 판단되면 "새 DB로 바꾸기"를 누른다. 그런데 이 버튼을 누르기 전에, 우리 서버들이 전부 같은 준비 상태를 보고 있는지 확인해야 한다.

2. 등장인물은 다섯 개다

이름이 어렵게 느껴져도 실제 역할은 단순하다. 아래 다섯 개만 알면 뒤 내용을 읽을 수 있다.

서비스고객 요청을 받는 앱이다. 여러 서버에 나뉘어 떠 있다.
현재 DB지금 서비스가 실제로 쓰는 DB다.
새 DB바꿔 탈 후보 DB다. AWS가 현재 DB 옆에 준비한다.
확인 버튼바꾸기 전에 서버들에게 준비됐는지 물어본다.
연결 도우미바꾸는 중 DB 연결이 흔들릴 때 앱 안에서 도와준다.

3. 전체 흐름은 이렇다

복잡한 내부 이름을 빼면 흐름은 아래 그림 하나로 볼 수 있다. 

flowchart LR
  A[현재 DB 사용 중] --> B[AWS가 새 DB 준비]
  B --> C[확인 버튼 실행]
  C --> D[모든 서버에게 물어봄]
  D --> E{모두 준비됨?}
  E -- 아니오 --> F[멈추고 이유 확인]
  E -- 예 --> G[새 DB로 바꾸기 실행]
  G --> H[연결 도우미가 전환 중 연결 보호]

4. 왜 확인 없이 바로 바꾸면 위험한가

AWS 화면에서 준비된 것처럼 보여도, 실제 서버나 DB 안쪽에서는 아직 덜 준비된 상태일 수 있다.

위험한 경우

겉으로만 준비된 상태

  • 새 DB 묶음은 보이지만 새 DB 자체는 아직 마무리 중일 수 있다.
  • 일부 서버는 새 DB 정보를 아직 못 볼 수 있다.
  • 주소가 아직 바뀌는 중이라 서버마다 다르게 보일 수 있다.
  • 그 상태에서 전환을 누르면 AWS가 거절하거나 서비스 연결이 흔들릴 수 있다.
확인 버튼의 목적

바꾸기 전 멈춰야 할 상황을 잡는다

  • 새 DB가 정말 사용할 수 있는지 본다.
  • 모든 서버가 같은 준비 상태를 보는지 본다.
  • 문제가 있으면 전환 버튼을 누르지 않게 만든다.
  • 왜 멈췄는지 운영자가 볼 수 있게 남긴다.

5. 실제 소스는 어떤 순서로 검증하나

flowchart TD
  A[POST /api/rds-bluegreen/readiness] --> B[RdsBlueGreenReadinessService.checkAndLog]
  B --> C{readiness-log enabled?}
  C -- false --> C1[ready=false
reason: readiness endpoint is disabled]
  C -- true --> D[attempts 만큼 반복]
  D --> E[collector.collectAwsDeployment]
  D --> F[collector.collectDatabaseAndDns]
  E --> G[fromSnapshots에서 AWS 조건 판정]
  F --> H[fromSnapshots에서 DB/DNS 조건 판정]
  G --> I{candidateReady?}
  H --> I
  I -- false --> J[consecutiveReady=0
reason에 실패 이유 기록]
  I -- true --> K[consecutiveReady + 1]
  K --> L{requiredConsecutive 도달?}
  L -- false --> D
  L -- true --> M[ready=true
reason: ready]
순서 실제 소스 검증 방식 실패 예시
1 checkAndLog() app.rds-bluegreen.readiness-log.enabled가 켜져 있는지 본다. ready=false, reason="readiness endpoint is disabled"
2 collectAwsDeployment() DescribeBlueGreenDeployments로 대상 Blue/Green 배포를 찾는다. 우선순위는 deployment id, 없으면 source/target ARN 필터다. reason="RDS API check failed: NotFound ..."
3 awsDeploymentReady() 배포 상태가 AVAILABLE 또는 SWITCHOVER_COMPLETED인지 본다. reason="RDS Blue/Green deployment is not AVAILABLE: PROVISIONING"
4 members.stream().allMatch(...) 전환 대상 멤버들이 모두 AVAILABLE 또는 SWITCHOVER_COMPLETED인지 본다. reason="one or more switchover members are not ready"
5 tasks.stream().allMatch(...) AWS 준비 작업이 모두 COMPLETED인지 본다. reason="one or more RDS Blue/Green preparation tasks are not completed"
6 collectDbInstance() DescribeDBInstances로 현재 DB와 새 DB 자체가 둘 다 available인지 본다. reason="source or target DB instance is not available: source=available, target=modifying"
7 DriverManager.getConnection() 앱 인스턴스가 실제 DB에 일반 JDBC로 접속 가능한지 본다. reason="database metadata check failed: ..."
8 select @@hostname, @@read_only, connection_id() 지금 연결된 DB가 쓰기 가능한 DB인지 본다. @@read_only=false여야 한다. reason="current regular JDBC connection is not writer"
9 select ... from mysql.rds_topology DB 안의 준비표를 읽고 최소 행 수 이상인지 본다. reason="mysql.rds_topology rows 0 < 2"
10 hasTopologyRole(..., "SOURCE/TARGET") 준비표 안에 현재 DB 줄과 새 DB 줄이 둘 다 있는지 본다. reason="source topology row is not visible yet" 또는 reason="target topology row is not visible yet"
11 InetAddress.getAllByName(row.endpoint()) 준비표에 나온 DB 주소들이 실제 IP로 풀리는지 본다. reason="one or more topology endpoints are not DNS-resolvable"
12 correspondingNodes() 현재 DB 줄과 새 DB 줄이 서로 짝이 맞는지 본다. 새 DB 이름에서 -green-xxxxxx를 제거해 현재 DB 이름과 비교한다. reason="source and target topology rows are not logically paired"
13 Collections.disjoint(sourceAddresses, targetAddresses) 현재 DB 주소와 새 DB 주소가 같은 IP를 보지 않는지 본다. reason="source and target topology endpoints do not resolve to distinct IP addresses"
14 consecutiveReady >= requiredConsecutive 위 조건이 한 번만 통과한 것이 아니라 설정한 횟수만큼 연속 통과했는지 본다. 기본값은 3회다. candidateReady=true라도 연속 횟수가 부족하면 아직 ready=false

  "ready": false,

  "awsDeploymentReady": true,
  "awsTasksReady": true,
  "awsDbInstancesReady": false,
  "dbConnectionOk": true,

6. 확인 결과는 이렇게 읽으면 된다

운영자가 모든 세부 값을 외울 필요는 없다. 아래 네 가지가 모두 맞으면 전환을 검토할 수 있다.

볼 항목 쉬운 뜻 통과 기준
전체 결과 확인한 서버가 모두 준비됐는지 allReady=true
서버 수 빠진 서버 없이 전부 확인했는지 예상 서버 수와 실제 확인 서버 수가 같아야 함
브랜드별 결과 브랜드가 여러 개여도 한쪽만 확인하고 넘어가지 않았는지 모든 브랜드가 준비 완료여야 함
실패 이유 준비가 안 됐다면 왜 안 됐는지 reason="ready" 또는 명확한 실패 이유

7. 연결 도우미는 무엇인가

연결 도우미는 확인 버튼과 다르다. 확인 버튼은 바꾸기 전에 쓰고, 연결 도우미는 앱 안에서 계속 동작하면서 바꾸는 순간의 DB 연결을 보호한다.

확인 버튼

전환 전 검사 담당

운영자가 전환 버튼을 누르기 전에 "지금 눌러도 되는 상태인가?"를 확인한다.

연결 도우미

전환 중 연결 보호 담당

앱이 DB에 연결하려는 순간, 지금은 기다려야 하는지 새 DB로 보내야 하는지 판단한다.

8. 둘의 차이는 이 표로 보면 된다

둘 중 하나만 있으면 충분하다고 보기 어렵다. 역할이 다르기 때문이다.

구분 확인 버튼 연결 도우미
언제 쓰나 새 DB로 바꾸기 직전 앱이 실행되는 동안 계속
무엇을 보나 AWS 상태, DB 상태, 서버별 준비 상태 DB 연결, 주소 변화, 전환 중 단계
잘하는 일 전환 전에 위험한 상태를 잡는다 전환 중 연결이 흔들릴 때 보호한다
못하는 일 전환 중 연결을 대신 보호하지는 못한다 운영자가 전체 서버 준비 상태를 한 번에 보는 화면은 아니다

9. 연결 도우미 기준으로 무엇을 덮었고 무엇이 빠졌나

연결 도우미가 전환 중에 모으는 정보 중, 전환 전에 미리 확인할 수 있는 것은 확인 버튼에 넣었다. 하지만 전환이 실제로 시작된 뒤에만 알 수 있는 동작은 확인 버튼이 대신할 수 없다.

덮은 것

전환 전에 볼 수 있는 준비 상태

  • AWS가 새 DB 묶음을 준비 완료로 보는지 확인한다.
  • 현재 DB와 새 DB가 둘 다 사용 가능한지 확인한다.
  • DB 안에서 현재 DB와 새 DB 정보가 같이 보이는지 확인한다.
  • 현재 DB 주소와 새 DB 주소가 서로 다른 곳을 가리키는지 확인한다.
  • 여러 서버가 모두 같은 결론을 내리는지 확인한다.
비슷하지만 완전히 같지는 않은 것

서버 지도 확인

  • 연결 도우미는 앱 안에서 현재 DB와 새 DB의 서버 지도를 계속 만든다.
  • 확인 버튼은 DB 안의 준비표를 읽고 현재 DB와 새 DB가 짝이 맞는지 확인한다.
  • 운영 판단에는 도움이 되지만, 연결 도우미 내부 동작과 완전히 같은 검사는 아니다.
빠진 것

전환 중에만 가능한 보호

  • 전환 중 새 연결을 잠깐 기다리게 하는 동작은 하지 않는다.
  • 전환 중 새 DB 쪽으로 연결을 대신 보내는 동작은 하지 않는다.
  • 기존 DB 연결을 닫거나 다시 연결하는 동작은 하지 않는다.
  • 전환 후 예전 주소가 완전히 사라졌는지 계속 추적하지 않는다.

10. 운영자는 실제로 이렇게 쓰면 된다

운영에서 중요한 것은 확인과 전환 사이의 시간을 짧게 두는 것이다. 확인하고 오래 기다리면 그 사이 상태가 바뀔 수 있다. 

sequenceDiagram
  participant Ops as 운영자
  participant Check as 확인 버튼
  participant App as 여러 서버
  participant Aws as AWS
  participant Helper as 연결 도우미

  Ops->>Aws: 새 DB 준비 시작
  Ops->>Check: 준비됐는지 확인
  Check->>App: 서버마다 직접 확인 요청
  App-->>Check: 준비됨 또는 문제 있음
  Check-->>Ops: 전체 결과 전달
  alt 모두 준비됨
    Ops->>Aws: 바로 새 DB로 바꾸기 실행
    Helper->>Helper: 전환 중 연결 보호
  else 하나라도 문제 있음
    Ops->>Ops: 멈추고 실패 이유 확인
  end

11. 이번 실험에서 실제로 확인한 것

이 문서는 단순 추정이 아니라 실제 AWS에 DB와 서버를 만들고 확인한 결과를 바탕으로 정리했다.

실험 1

서버 4대 확인

처음에는 새 DB가 아직 완전히 준비되지 않아 확인이 실패했다. 조건을 보강한 뒤 준비 완료를 확인하고 전환까지 완료했다.

실험 2

서버 8대와 여러 브랜드 확인

서버 수를 늘리고 브랜드를 나눠 확인했다. 모든 서버가 준비 완료라고 답한 뒤 바로 전환했고 완료됐다.

12. 어려운 말은 이렇게만 이해하면 된다

실제 운영 문서나 로그에는 영어 이름이 남아 있을 수 있다. 아래 뜻으로 읽으면 된다.

  • Blue는 현재 쓰는 DB다.
  • Green은 새로 준비한 DB다.
  • 스위치오버는 새 DB로 바꾸는 버튼이다.
  • Readiness API는 준비됐는지 물어보는 확인 버튼이다.
  • Wrapper는 앱 안에서 DB 연결을 도와주는 연결 도우미다.
  • DNS는 DB 주소록이다. 주소록이 늦게 바뀌면 서버가 예전 DB를 볼 수 있다.
  • Topology는 DB 자리표다. 현재 DB와 새 DB가 어떤 이름으로 보이는지 적혀 있다.

13. 결론

확인 버튼만 믿어도 되는 부분

새 DB로 바꾸기 전에 모든 서버가 같은 준비 상태를 보고 있는지 확인하는 용도로는 의미가 있다. 특히 서버 수, 브랜드별 결과, AWS 준비 상태, DB 안쪽 준비표를 함께 보기 때문에 수동 전환 전 마지막 확인으로 쓸 수 있다.

확인 버튼만으로 끝내면 안 되는 부분

확인 버튼은 전환 중 연결을 직접 보호하지 않는다. 운영계에서는 확인 버튼으로 마지막 확인을 하고, 앱 안에서는 연결 도우미를 켜 둔 상태로 전환하는 구성이 더 맞다. 

flowchart LR
  A[확인 버튼] --> B[전환 전 준비 확인]
  C[연결 도우미] --> D[전환 중 연결 보호]
  B --> E[둘 다 있어야 운영 판단이 쉬움]
  D --> E
  E --> F[확인 직후 바로 새 DB로 바꾸기]
